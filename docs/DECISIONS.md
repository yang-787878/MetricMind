## 4. 数据与工具口径（阶段 2）

| # | 决策 | 理由 | 与任务书的差异 |
|---|---|---|---|
| D9 | `export_report` 推迟到阶段 4 实现，阶段 2 注册 6 个工具 | §11 阶段 4 明确包含 `charts.py`（SVG 渲染）与 `exporter.py`；导出工具没有这两者只能产出半成品 | §11 阶段 2 的"7 个工具"在本阶段实际为 6 个，阶段 4 补齐第 7 个 |
| D10 | `identifier` 语义类型额外要求列名带 `id` / `编号` / `code` 痕迹 | 否则小样本里取值互不相同的整数指标（如 revenue）会被判成标识符，导致候选指标列表失真 | §8.7 的"唯一率 > 0.98 且为整型或字符串"在此收紧 |
| D11 | `share` 必须提供 `group_by`；`growth_rate` 必须提供 `agg` | 无分组的 share 恒等于 1、无 agg 的 growth_rate 无法确定聚合口径，属于"看起来能跑但语义错"的定义 | §5.2(4) 只写了"要求 date_column + period + agg 齐备"，这里补上 share 的约束 |
| D12 | `ratio` / `rate` 支持 `group_by`（分组内分别计算比率） | "各渠道转化率有什么区别"这类问题是评测用例之一，必须成立 | §5.2(4) 未明确 ratio 是否可分组 |
| D13 | CSV 表头重复用 `csv` 模块直接读第一行检测，而不是依赖 pandas 的列名 | pandas 会把 `a, a` 自动改成 `a, a.1`，等发现时问题已被掩盖 | 无 |
| D14 | `DUPLICATE_ROWS` 只统计"完全重复的行"；`order_id` 这类主键重复通过 `distinct_count < row_count` 体现 | §5.2(2) 的问题码是固定 8 个，没有"主键重复"码；另立新码会破坏契约 | 无 |
| D15 | 工具调用次数预算统一在 `registry.execute_tool` 拦截，`ToolSpec.max_calls_per_run` 是唯一来源 | 任何节点/工具都无法绕过统一入口，§5.1 的上限才不会形同虚设 | 无 |
| D16 | 营销漏斗示例数据采用 **52 个 ISO 周 × 5 渠道 = 260 行** | 任务书同时要求"约 260 行"与"26–30 周 × 5–9 渠道"，在固定 5 渠道时 26–30 周只有 130–150 行，两个约束数学上不可同时满足；行数与渠道语义对演示更重要 | §9.1 的"26–30 周"未满足，如需 26–30 周则须减少行数或增加渠道 |
| D17 | 示例销售数据按"月份 × 渠道 × 品类配额 + 分层抽样"生成，所有植入模式（-18% 降幅、DTC -25%、Home 折扣抬升、Outlet 退货率、5 类质量问题计数）都写成常量 | 纯随机生成无法稳定命中 ±2pp 的目标区间；配额化后两次运行 sha256 完全一致，演示与评测才可复现 | 无 |

## 5. Agent 工作流（阶段 3）

| # | 决策 | 理由 | 与任务书的差异 |
|---|---|---|---|
| D18 | 数字审计判定：**有候选值但未命中** → `unsupported`（附最接近值）；**证据存在但没有任何数值** → `unverifiable`；无证据 / 证据不存在 → `unsupported` | §5.2(6) 只对"1% 内超差"给了 unsupported，且把"无任何候选"判为 unverifiable；但 §10.1 明确要求"超差 2% * unsupported*"。两处冲突时以"有候选就必须给出最接近值"为准，避免大量结论被标成无法验证 | §5.2(6) 的 1% 近似阈值仍保留在常量 `NEAR_TOLERANCE` 中用于文案，但不再决定状态 |
| D19 | `partial` 终态的 SSE 事件沿用 `run_succeeded`，`payload.status="partial"` | §6.5 只定义了 succeeded/failed/cancelled 三种终态事件，而 partial 确实产出了可用报告；新增事件类型会破坏前端契约 | 无（事件名不变，前端按 payload.status 渲染） |
| D20 | 计划中的结果依赖用占位符 `"$step:s2"` / `"$last_result"` 表达，执行时解析成真实 `result_id` | 计划生成时不可能知道未来的 result_id；若允许模型编造 result_id，§5.2(5) 的"图表必须引用真实结果"就会被绕过 | 无（占位符由执行器替换，工具层仍然只接受真实 result_id） |
| D21 | 计划步骤数超过 `max_steps` 时**截断并记 warning**，而不是让整次运行失败 | 预算的意义是限制执行量，不是让分析直接失败；截断后仍能产出部分结论 | §6.2 只要求"预算耗尽 → partial + limitations" |
| D22 | 阶段 3 引入 `services/report_builder.py` 的最小实现（KPI/方法论/质量/降级），图表 SVG 与 HTML/MD 导出留在阶段 4 | 阶段 3 的出口标准要求"产出带 KPI/图表/证据的报告 JSON"，没有装配层就无法验证闭环 | §11 把 report_builder 放在阶段 4；实际提前实现，阶段 4 只做增强不重写 |
| D23 | 报告生成失败（模型不可用/输出非法）时退回 `demo_planner` 的确定性模板，状态置 `partial` 并在 limitations 注明 | §6.3 的失败策略要求"用确定性模板生成仅含工具事实的报告"，而不是让整次运行失败 | 无 |
| D24 | 取消：节点间检查点抛 `RunCancelled`，runner 兜底写 `cancelled` 并保留已产生事件与证据 | §6.6 要求取消后仍可查看中间结果；进程内 `asyncio.Event` 比在节点里轮询数据库更可靠 | 无 |
