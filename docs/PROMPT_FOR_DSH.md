# 项目材料

## 一句话定位

MetricMind —— 自然语言提问 → Agent 输出结构化分析计划 → 受控工具做确定性计算 → 带证据链的数字审计报告 → 自包含单文件 HTML 导出。
核心主张是三个词：**计划可见、计算受控、数字可审**。

## 技术栈

- 后端：Python 3.12 / FastAPI / Pydantic v2 / LangGraph（StateGraph）/ DuckDB / pandas / sqlglot / SQLite / Jinja2
- 前端：React 18 / TypeScript / Vite / Tailwind CSS / Recharts / vitest / Playwright
- 部署：Docker Compose（Nginx 容器托管前端并反代 /api，uvicorn 容器跑后端）
- 模型接入：OpenAI 兼容协议，可替换 DeepSeek / Moonshot / vLLM，模型名不硬编码

## 核心机制（这些都是真实实现，可以落到文件/函数）

1. **8 节点状态机**：intake → inspect → plan → execute → verify → report → audit → finalize。
   支持单步修复（`repair_step`：工具参数错误时修正后重试，修不好就跳过）、
   条件重规划（`replan`：verify 发现失败或无证据且还有重规划余量）、
   预算耗尽降级（`finalize` + `partial` 状态 + `budget_warning` 事件）。
2. **7 个受控工具**，每个都有 Pydantic 参数 schema 和"每 run 调用次数上限"：
   `inspect_dataset`(≤2) / `profile_dataset`(≤2) / `query_data`(≤6) / `calculate_metrics`(≤8) /
   `create_chart`(≤5) / `verify_result`(≤3) / `export_report`(≤2)。
   产出数据或图表的工具会生成 `result_id`，进入证据池。
3. **四道数据真实性关卡**（这是项目最核心的设计）：
   - 关卡 1：模型看不到原始 DataFrame，只拿到字段摘要 + 每列 ≤3 个样例值（`nodes/inspect.py` → `nodes/plan.py::_plan_payload`）
   - 关卡 2：图表工具只接受 `from_result_id`，没有"直接传数据数组"的入口，列名必须真实存在（`tools/create_chart.py` + `services/charts.py::build_chart_spec`）
   - 关卡 3：服务端独立 verifier 逐条核对 claim 里的每个数字与证据值，容差 0.5%，不通过就降级写进 limitations（`nodes/audit.py` + `services/verifier.py::verify_claims`）
   - 关卡 4：最终渲染的 KPI / 结论数字用证据值重新格式化，同时保留 `claimed_value` 供前端对比（`services/report_builder.py::build_report`）
4. **SQL 安全**：sqlglot 解析成 AST 后走白名单校验，只允许查单表 `data` 视图，函数和语句类型有黑名单，
   DuckDB 侧设 `enable_external_access=false` 并禁止自动加载扩展（`services/sql_guard.py` + `services/engine.py`）。
5. **双模式**：Live 用 LLM 产出 `StructuredPlan`（JSON Schema 严格模式 + 1 次修复重试）；
   Demo 用确定性的 `demo_planner` 按字段结构生成计划，同一数据集同一问题两次运行结果完全一致（除时间戳）。
   两种模式下工具执行都是真实的 DuckDB / pandas，Demo 不是假数据演示。
6. **运行与流式**：请求线程只负责落库和返回，运行由后台 task 持有，客户端断开不会取消运行；
   事件以 SQLite 为真相源，支持 `after_seq` 断线续播，进程内 EventBus 只负责"实时"这一层；SSE 推事件。
7. **并发与资源控制**：全局 Semaphore(2)、单 run 240s 超时、支持取消、按 IP 6 次/分钟限流、
   上传限制 25MB / 20 万行 / 60 列。
8. **预算**：单次运行 10 步 / 16 次工具调用 / 2 次重规划 / 240 秒，任一项耗尽都会出 `budget_warning`。

## 量化事实（简历里只能用这些数字，一个都不许编）

- 后端 pytest **127 passed / 约 25s**；分布：SQL 守卫 39、工具 17、指标 16、loader 13、API 12、验证器 9、导出 7、事件 5、重规划 3、取消 2、确定性 2、评测 1
- 自建评测集 **9/9 通过（100%）**，覆盖：归因分析、结构分析、对比、数据质量、不可回答、越权请求、漏斗转化、漏斗收入、地区结构
- 前端 vitest **31 passed / 约 2.2s**；`tsc --noEmit` 通过
- E2E（Playwright / Chromium）**3 passed**：主线（计划→工具→图表→报告→导出下载）+ 非法上传 + Live 未配置提示
- 前端构建产物：index 116.4kB / charts chunk 407.6kB / css 30.7kB（charts 已单独分包）
- 示例数据 7,180 行 × 14 列；`calculate_metrics` 支持 11 种确定性指标
- 主 demo 问题："为什么 2025 年 9 月销售额相比 6–8 月下降了？"，产出 KPI ¥1970.3 万、同比 -18.9%
- 导出 HTML 为完全自包含单文件：内联 CSS + 内联 SVG，无外链、无 JS，断网可打开

## 已知限制（面试官一定会往这里戳，必须诚实）

- **单表**：一次分析只针对一个 CSV/XLSX，不做多表 join
- **无多轮对话**：不做长对话记忆，改问题 = 新建一次运行
- **无权限体系**：无登录、无多租户、无计费
- **SQL 守卫是白名单不是沙箱**：基于 sqlglot AST + DuckDB 执行隔离，不是 OS 级沙箱
- **Demo 模式叙述是模板**：与问题措辞无关，只能证明"流程与数字可信"，不能证明"模型理解力"
- **Live 模式未在交付环境实测**：交付环境没有 API Key，`LLM_UNAVAILABLE` 重试与降级是代码级实现、非实测
- **评测规模小**：9 条用例只能证明典型路径正确，不证明泛化能力
- **E2E 只覆盖 3 条**：取消与断网降级仅单测覆盖
- **未接入**：不解析 PDF/Word、无 OCR、不抓网页、不连实时数据库

# 输出要求

严格按下面三部分输出，用中文，多用表格和列表，不要大段散文。

## 第一部分：简历项目描述

产出 4 种形态：

1. **电梯陈述**：1 句话，≤30 字，用于自我介绍开场或简历项目标题下一行
2. **1 行版**：≤40 字，用于简历空间极紧张时
3. **3 条 bullet 版**：每行 ≤45 字
4. **5 条 bullet 版（主推）**：每条 50–70 字，结构是「动作 + 技术手段 + 可验证结果」

硬要求：

- 每条 bullet 必须至少含 1 个上面「量化事实」里的真实数字，不许编造任何新数字
- 动词开头：设计 / 实现 / 定位 / 重构 / 收敛，禁止"负责""参与""协助"开头
- 禁止"精通""熟练掌握""深入理解"这类无信息量形容词
- 不许把 README 原话搬过来改个主语，必须转成第一人称成果句
- 5 条 bullet 后面标注：哪几条更适合投【AI 应用开发岗】，哪几条更适合投【后端/全栈岗】
- 额外给一段 200 字左右的「项目背景补充」，用于面试口述：为什么做这个东西、想解决什么真实痛点

## 第二部分：面试问题

按 4 类分，**每类 6–8 题**。每题给 4 个字段：

| 字段 | 要求 |
|---|---|
| 问题原文 | 写成真实面试官会开口问的原话，不要论文标题 |
| 考察意图 | 一句话说清他到底想验证什么能力 |
| 标准答法 | 结合本项目回答，必须能落到具体文件 / 函数 / 数字；3–6 句，说人话 |
| 大概率追问 | 1–2 条，是他听完标准答案会接着问的 |

四类：

- **A. 架构与选型**：为什么这么选、被否的方案是什么、换一个场景还成立吗
- **B. 实现深挖**：会追问到代码细节、数据结构、状态流转、异常分支
- **C. 边界与失败**：如果你说的保障不成立会怎样、最坏情况、数据量涨 100 倍
- **D. 压力题 / 反常识**：例如"这不就是调个 API 套壳""数字审计是不是自己检查自己""你这评测 9 条能说明什么""如果模型坚决要编数字呢"

每题标注难度标签：`必答` / `加分` / `可能翻车`。
标 `可能翻车` 的题目，必须额外写一句"**为什么容易翻车**"和"**最低防守答法**"（哪怕答不全也不至于崩）。

## 第三部分：学习清单

分三档，每档用表格：

1. **面试前必须补**（不补会当场卡住、直接影响评价）
2. **想加分就补**（能明显抬高档次，但面试官不一定问）
3. **长期补**（这项目暴露出的真实能力缺口）

每项写 4 列：**知识点 / 为什么这个项目会让你被问到它 / 学到什么程度算够用 / 预计耗时**。
"学到什么程度算够用"必须具体，例如"能手写一个带 GROUP BY 的窗口函数并解释执行顺序"，不能写"了解 SQL"。

然后单独给两段：

- **真实短板 vs 可辩护的取舍**：把「已知限制」里每一条归类。属于取舍的要给出正面回应话术（例如单表 → "这是刻意的范围收敛，多表 join 会破坏单表口径可验证性，扩展路径是先做 join 白名单"）；属于真短板的直接说"这个必须补，没法圆"
- **3 天冲刺计划**：假设面试在 3 天后，按天排出「上午 / 下午 / 晚上」该学什么、该背哪几道题、该手写哪段代码

# 硬约束

1. 只许使用我给出的技术和数字。需要项目里没有的信息时，明确写「**需本人确认**」，不许猜
2. 简历句优先用数字和机制，不用形容词堆砌
3. 面试答案必须可追溯：能指出文件/函数/事件名/字段名，禁止"通过一系列优化提升了性能"这种空话
4. 如果某个问题我大概率答不上来，直接说，并给出最低成本的学习路径，不要假装我会
5. 不要输出励志话术、不要总结"这个项目很有价值"，直接给内容

## 使用说明

1. 把开头 4 个 `【】` 占位符换成真实情况 —— **这一步最影响质量**，dsh 会据此决定措辞强度。
2. 如果 dsh 能读仓库，让它先读 `docs/INTERVIEW_QA.md`，避免和已有 15 条重复。
3. 拿到结果后重点看第三部分「真实短板 vs 可辩护的取舍」—— 这一段决定你面试时是主动引导还是被动挨打。
4. 如果 dsh 一次输出太长被截断，拆成三轮问：「只出第一部分」→「只出 A/B 类问题」→「只出 C/D 类 + 学习清单」。
